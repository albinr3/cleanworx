# Module 4 — Offer Creation

## Scope

This module combines the explicit offer principles taught in the video with the functional workflow later described by Diego's own custom offer GPT. For the step-by-step research and offer-generation engine, also read `09-offer-gpt-engine.md`.

The custom GPT's hidden system instructions are not available, so this skill should not claim to be a literal clone. However, the documented workflow is sufficient to reproduce its main functional process.

## Value model taught

Diego describes offer value using a structure equivalent to:

**(desired result × perceived probability of achieving it) / (time × effort or sacrifice)**

Use this directionally rather than as a literal calculation.

The practical goal is therefore to:

- increase desirability and specificity of the result,
- increase confidence that the buyer can achieve it,
- reduce avoidable time to meaningful progress,
- reduce avoidable client effort/sacrifice.

## Offer positioning philosophy

Diego pushes against turning “irresistible offers” into a competition over who stacks the most bonuses or extreme guarantees.

His preferred logic is:

**problem structure → correct solution path → confidence → offer**

The buyer should see the offer as a logical and credible path to the desired result, not merely a large stack of features.

## Research before architecture

Before designing deliverables, use this functional sequence from Diego's custom GPT:

**Niche → main problem → ~35 mini-problems → 3 pillars → mechanism → 3 offer options → strongest offer**

The mini-problems should include relevant:

- obstacles,
- frustrations,
- fears,
- mistakes,
- desires,
- knowledge gaps,
- execution barriers,
- purchase barriers,
- previous failed attempts.

Treat inferred mini-problems as hypotheses unless supported by actual market/customer data.

## Three-pillar model

Group the problem map into three meaningful solution pillars.

The pillars should explain the path to the result. They are not just categories for organizing deliverables.

For each pillar determine:

- which problems it solves,
- which are root causes vs symptoms,
- what must happen first,
- how the pillar contributes to the final outcome,
- what could cause the pillar to fail.

## Solution mechanism

Translate the pillars into a simple methodology/mechanism that explains how the service gets the buyer from current state to desired state.

A strong mechanism improves communication and perceived likelihood because the buyer understands the logic of the path.

## Build 3 distinct offers

Create three meaningfully different ways to package the solution. Vary dimensions such as:

- scope,
- speed,
- support,
- level of implementation,
- specialization,
- delivery model,
- risk reduction,
- or primary positioning.

Do not create three names for the same package.

## Architecture of an offer

A complete offer can include:

- target buyer,
- main result,
- problem being solved,
- mechanism/methodology,
- three pillars,
- deliverables,
- benefits,
- support/accountability,
- DFY/DWY/DIY split,
- bonuses only when useful,
- friction reduction,
- proof requirements,
- risk-reduction elements when appropriate,
- duration,
- pricing direction,
- positioning.

## Strategic analysis

Do not stop at packaging. Explain:

- which mini-problems matter most,
- which one is the bottleneck,
- which should be solved first,
- why previous attempts tend to fail,
- which offer components increase perceived probability,
- which reduce time/effort,
- which create delivery burden.

## Selecting the strongest offer

Compare the three offers using:

- clarity of outcome,
- urgency of problem,
- ease of communication,
- differentiation,
- perceived value,
- perceived likelihood of success,
- reduction of time and effort,
- fit with the buyer,
- fulfillment feasibility,
- ability to generate strong client results/proof.

Select the strongest commercial option when the user asks for a recommendation.

## Delivery models

### Done For You (DFY)
Provider executes the work. This often lowers buyer effort and can make the offer easier to sell, but increases fulfillment load.

### Done With You (DWY)
Provider guides and collaborates with the client. Diego favors this as an important middle ground.

### Done Yourself (DIY)
Provider teaches; client executes. This scales more easily, but increases required client effort and can reduce sellability/completion.

## Hybrid delivery recommendation

Diego recommends combining models:

- critical technical elements that strongly determine results → **DFY**,
- ongoing implementation, review, accountability, coaching, optimization → **DWY**,
- transferable knowledge/resources and safe repeatable actions → **DIY**.

This aims to reduce failure risk while preserving scalability.

## Sellability + scalability

Every offer must pass two tests:

### Sellability
- Does the buyer strongly want the result?
- Is the promise clear?
- Does the path feel credible?
- Does the offer reduce effort/time?
- Does it solve urgent, weighted problems?

### Deliverability / scalability
- Which parts require expert labor?
- Which parts can be standardized?
- What becomes the bottleneck at 2× or 5× volume?
- How many clients can the team support?
- Does the offer create excessive custom work?
- Are client dependencies likely to block results?

A commercially attractive offer that cannot be fulfilled consistently is not a strong offer.

## Pricing

The custom GPT can discuss pricing, but Diego explicitly recommends not outsourcing the final price decision blindly to AI.

Use pricing context such as:

- value of the result,
- buyer purchasing power,
- urgency,
- proof,
- delivery burden,
- duration,
- degree of implementation,
- market context,
- validated historical prices.

When evidence is insufficient, provide a range or pricing logic rather than a false-precision number.

## Results as growth engine

Client results later create:

- case studies,
- referrals,
- authority,
- content,
- stronger sales proof,
- easier future acquisition.

Therefore design the offer to maximize the probability of real client success, not only initial conversion.
