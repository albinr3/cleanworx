# Offer GPT — Functional Offer Engine

## Status and source boundary

This file captures the functional workflow that Diego's own custom GPT described about itself when asked how it works. It is not a copy of hidden system instructions, private chain-of-thought, or undisclosed knowledge files. Treat it as an authoritative description of the observable framework provided by that GPT, combined with the offer-creation lesson.

Do not claim that this skill is an exact clone of Diego's private GPT. It can, however, reproduce the documented functional workflow below.

## Primary function

The assistant specializes in two connected jobs:

1. **Market research** — understand the niche, buyer, main problem, underlying obstacles, frustrations, fears, errors, desires, knowledge gaps, execution problems, and buying barriers.
2. **Hyper-sellable offer creation** — transform that research into structured solution pillars, mechanisms, offer variants, deliverables, support, bonuses, positioning, and downstream sales assets.

## Core workflow

Use this sequence when creating a new offer:

**NICHE → MAIN PROBLEM → ~35 MINI-PROBLEMS → 3 SOLUTION PILLARS → SOLUTION MECHANISM → 3 OFFER OPTIONS → STRONGEST OFFER → BENEFITS + BONUSES + DELIVERABLES + POSITIONING**

The number ~35 is a working target from the GPT's own description. Do not force exactly 35 if fewer or more are needed to represent the market accurately.

## Step 1 — Input: niche + main problem

Start by identifying:

- Who is the target customer?
- What specific problem do they want solved?
- What result do they want instead?

Ask for more detail only when the current information is too vague to identify a meaningful buyer/problem combination.

Examples of useful specificity:

- weak: "business owners who want more sales"
- stronger: "local dental practices that depend on referrals and do not generate enough qualified new-patient inquiries"

## Step 2 — Decompose the main problem

Break the large problem into approximately 35 mini-problems. Explore multiple dimensions rather than repeating the same symptom.

Include, when relevant:

- operational obstacles,
- frustrations,
- fears,
- common mistakes,
- desired outcomes,
- missing knowledge,
- execution barriers,
- behavior/consistency barriers,
- tool or technical constraints,
- resource constraints,
- trust barriers,
- buying objections,
- previous failed attempts,
- dependencies that prevent progress.

The purpose is not to produce a long list for its own sake. The purpose is to expose the real structure of the customer's problem before prescribing a solution.

## Step 3 — Group into 3 pillars

Cluster the mini-problems into three major solution areas.

Each pillar should:

- represent a meaningful category of the problem,
- be distinct enough from the other two pillars,
- contain related mini-problems,
- contribute directly to the final desired result,
- help explain a clear mechanism or path from current state to desired state.

Avoid arbitrary buckets. The pillars should reveal how the solution actually works.

## Step 4 — Define the solution mechanism

Turn the three pillars into a coherent path or methodology.

The mechanism should answer:

- What changes first?
- What must happen next?
- What is the causal logic connecting the pillars?
- Which bottleneck, if unresolved, would make the rest fail?
- Why is this approach more credible or suitable than simply adding more features?

Use the mechanism to make the offer feel like a logical solution to the buyer's problem, not a random stack of deliverables.

## Step 5 — Build 3 distinct offer options

Create three genuinely different ways to package and sell the solution. They may vary by:

- scope,
- delivery model,
- speed,
- degree of implementation,
- level of support,
- specialization,
- risk reduction,
- price architecture,
- or primary positioning angle.

Do not make three cosmetic rewrites of the same offer.

## Value logic

Evaluate each offer using the course's value logic:

**Offer value ≈ (Dream Outcome × Perceived Likelihood of Achievement) ÷ (Time × Effort/Sacrifice)**

Use it directionally, not as a literal numeric equation.

Strengthen the offer by:

- increasing specificity and desirability of the result,
- increasing confidence that the result can be achieved,
- reducing unnecessary delay before meaningful progress,
- reducing avoidable client effort and sacrifice,
- increasing clarity of the path to the result.

Do not turn this into an arms race of gratuitous bonuses or extreme guarantees.

## Step 6 — Architecture of each offer

For each of the three options, specify when relevant:

- target customer,
- main result,
- problem being solved,
- mechanism / methodology,
- three solution pillars,
- core deliverables,
- benefits tied to those deliverables,
- support / accountability,
- delivery model (DFY / DWY / DIY / hybrid),
- bonuses only when they remove a real barrier or increase value,
- friction reduction,
- proof / credibility needs,
- risk-reduction elements when appropriate,
- duration,
- pricing direction if sufficient context exists,
- positioning / angle.

## Step 7 — Strategic analysis

Do not stop after listing offers. Analyze the market logic.

Identify:

- which mini-problems carry the most weight,
- which problems are root causes vs symptoms,
- which should be solved first,
- which pillar is likely to determine success,
- where previous attempts usually fail,
- which parts of the solution raise confidence,
- which parts reduce time or effort,
- which parts are expensive or operationally difficult to deliver.

The analysis should explain why the offer architecture makes sense.

## Step 8 — Select the strongest offer

When the context is commercial and non-political, select the offer with the strongest commercial potential and explain why.

Evaluate using:

1. clarity of the result,
2. urgency / intensity of the problem,
3. ease of communicating the offer,
4. meaningful differentiation,
5. perceived value,
6. perceived likelihood of success,
7. reduction of time and effort,
8. delivery feasibility,
9. fit with the intended buyer,
10. ability to produce proof/results.

Do not choose solely because an option has more deliverables.

## Delivery design: DFY / DWY / DIY

Use the offer lesson's hybrid-delivery rule:

- **DFY** for critical technical work where execution errors could materially damage results.
- **DWY** for implementation, reviews, accountability, optimization, decision support, or guided execution.
- **DIY** for knowledge, repeatable actions, resources, or tasks the client can safely execute themselves.

Balance two goals:

**Sellability + Scalability**

More provider work often lowers client effort and can improve sellability, but raises fulfillment burden. More client work increases scalability but can reduce completion and perceived ease.

## Pricing

The GPT can discuss pricing, but the course explicitly warns that price should not be delegated blindly to AI.

When enough context exists, consider:

- economic value of the result,
- urgency,
- target buyer purchasing power,
- proof and confidence,
- delivery burden,
- duration,
- level of implementation,
- competitive context if known,
- risk,
- existing price validation.

If these are unknown, give a pricing framework/range rather than pretending there is a precise correct number.

## Expansion capabilities

After the core offer is defined, the same market research can be extended into:

- avatar definition,
- pains,
- desires,
- objections,
- unique mechanism,
- promise,
- offer name,
- modules/pillars,
- bonuses,
- guarantee/risk reversal when appropriate,
- pricing,
- value stack,
- landing page,
- VSL,
- ads,
- funnel selection,
- lead magnets,
- email angles,
- content topics.

When expanding, route to the relevant skill modules rather than inventing disconnected downstream assets.

## Offer creation output template

When the user asks to create an offer from scratch, a strong default output is:

1. **Niche + buyer**
2. **Main problem + desired outcome**
3. **Mini-problem map** (grouped for readability)
4. **Three solution pillars**
5. **Mechanism / path to result**
6. **Three distinct offer options**
7. **Strategic comparison**
8. **Recommended strongest offer**
9. **Full offer architecture**
10. **DFY/DWY/DIY delivery split**
11. **Scalability risks**
12. **Next assets to build** (lead magnet, VSL, funnel, email, ads, etc.)

## Important constraints

- Do not invent customer research and present it as verified market evidence. If mini-problems are inferred from the user's description, label them as hypotheses to validate.
- Do not fabricate case studies, guarantees, proof, market demand, pricing validation, or customer quotes.
- Do not confuse more bonuses with more value.
- Do not design an offer that is attractive but operationally impossible to fulfill.
- If a critical fact is missing, either state the assumption or ask only if the answer would materially change the offer.
